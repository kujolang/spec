# Spec security hardening follow-up

## Repository and scope

The clean starting point on `kujolang/spec` branch `main` was `b0c24a71b68a84d7f772d396697edb3ee22d62a2`. The ending implementation was `6000382546b3c57558dedd61dba91cd07538e1c2`. This is a follow-up to the [previous audit](spec-security-hardening-2026-11-26.md).

Spec defines task contracts. Bash dispatches the CLI, Python handles filesystem and JSON operations, and Kujo parses and renders documents. The review followed source and destination paths through parsing, output generation, discovery, validation, and release verification. It also checked GitHub CLI arguments, cache ownership and publication, status updates, CI annotations and permissions, the pinned runtime installer, and Eval and Dispatch exports.

## Findings and changes

| ID | Priority | Boundary | Evidence and resolution |
| --- | --- | --- | --- |
| SPEC-1 | P0 | Python module loading | CLI helper invocations could resolve imports from the working directory or `PYTHONPATH`. The CLI now invokes Python in isolated mode. The regression check uses inert workspace module names and verifies that a real UUID is generated. |
| SPEC-2 | P0 | JSON import | File conversion and stdin imports could parse unbounded input or interpolate keys into YAML/TOML syntax. One importer now bounds reads, requires an object, quotes keys, serializes before opening the destination, and creates it exclusively. Coverage checks both sources, all formats, literal keys, oversized input, non-objects, and nonregular files. |
| SPEC-3 | P0 | Validation gates | `ci` and `validate-all` consumed discovery via process substitution, which discarded scanner failure status. The Python validator could raise on an invalid dependency type and lose sibling results. Both commands now check discovery before consuming paths, and invalid dependency types fail only their own record. Coverage checks serial and parallel reports and a simulated scanner I/O failure. |
| SPEC-4 | P0 | Output integrity | Conversion and Eval export opened the destination before generation completed. A failure could truncate existing output. Both commands stage generated bytes first. Coverage checks preservation after conversion or export fails. |
| SPEC-5 | P0 | Release verification | Verification scripts built shell or Python source from paths or numeric settings. The benchmark and fuzz harnesses also used predictable scratch locations. The scripts now pass arguments directly and use private scratch directories. Numeric inputs are checked before fixture creation. |

## Compatibility and review coverage

The public schema, CLI command names, configuration variables, and report fields remain the same. Both JSON import sources now require an object of at most 1 MiB and honor `--name`. TOML import rejects JSON null because TOML has no corresponding value. The importer expects a new destination. A PyYAML installation visible only in the user-site directory is unavailable in isolated mode. Spec still supports its built-in YAML creation fallback.

The review covered malformed input, resource bounds, failure status, filesystem and process boundaries, scratch cleanup, output determinism, dependency and CI integrity, and the existing test and documentation contracts. Agent-facing Markdown, Dispatch and Eval payloads carry source data. Downstream consumers control any execution of that data. Spec has no model-provider calls, MCP registration, retries or workflow replay on these paths. Broader refactoring, runtime internals, release publication, and memory, token or binary-size benchmarking were outside this security pass. There were no package dependency changes or required changes in other repositories.

## Verification

Both acceptance trees were checked with the same checksum-verified Kujo 1.1.0 runtime and Bash 5.3, with scratch directories on a local volume with free space. The preliminary run with workstation defaults was affected by low disk space and used a different Kujo version, 1.5.0.

The aggregate gate retry with `SPEC_TIMEOUT=90 SPEC_BENCH_PROFILE=ci-macos SPEC_BENCH_BASELINE_SECONDS=90 SPEC_FUZZ_ITERATIONS=1 bash scripts/release_quality_gates.sh` passed all 20 gates, including all 117 CLI checks. The first run discarded the CLI suite output, so its failing check could not be identified. The final gate prints test diagnostics when this stage fails. A separate native Bash 3.2 smoke test passed parallel CI on the examples.

The installed launcher passed strict validation after a local-source installation. A one-file benchmark and one-iteration fuzz run both passed with the previous scratch paths already occupied, and both original paths were preserved.

All four focused security regression checks passed. Shell syntax checks, Python AST parsing, generated command inventory verification, `git diff --check`, and targeted invalid benchmark and fuzz option checks also passed.

The benchmark timings are single-run budget observations under variable workstation load. In three additional interleaved 100-file `validate-all` runs per tree with identical input, the baseline took 2.227–4.500 s (median 2.494 s) and the final tree took 1.808–3.268 s (median 2.877 s). All six runs validated 100 files. The overlapping observations do not establish a performance trend.

No unresolved high-confidence issue remained in the changed paths. The filesystem assumptions and runtime trust boundary in [SECURITY.md](../../SECURITY.md) still apply.
